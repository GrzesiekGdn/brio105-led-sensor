# brio105-led-sensor

A 3D-printable clip and sensor pod that detect when a **Logitech Brio 105** webcam is in use — by *watching the camera's own activity LED*, not by asking the operating system.

---

## 🎯 Why

The obvious way to know whether your webcam is running is to ask the OS. That is what
[micam-watcher](https://github.com/GrzesiekGdn/micam-watcher) does, and if you can install
your own software on the machine, it is the better answer — see
[Alternative](#-alternative-if-you-can-install-software) below.

But on a **corporate / locked-down machine** you often cannot:

- no admin rights, no installing a background service
- no writing to the registry, no systemd user units
- endpoint protection that flags anything watching `/dev/video*` or camera registry keys
- and it may simply be against your employer's IT policy

The camera itself has no such restriction. Every Brio 105 lights a small LED whenever the
sensor is streaming — that signal is generated by the camera's own firmware, it is always
correct, and reading it requires touching nothing on the host at all.

So: clip a phototransistor over that LED, shroud it from ambient light, and read it with a
microcontroller that has no connection to the work machine whatsoever. The corporate laptop
never knows the sensor exists — no software installed, no policy violated, no privileged
access needed. It works with any camera and any OS, since the only thing being observed is
a lamp.

Typical use: turn on a "busy" light outside the room, or set a Home Assistant presence flag,
while you are on a call.

## 📐 Where the camera geometry came from

The parts have to fit the camera closely — a shroud that leaks ambient light is useless — so
the design is built on a real mesh of the camera, not on guesswork.

1. **No public CAD model exists** for the Brio 105. GrabCAD, STLFinder and Printables only
   carry mounts for other Brio models, and Logitech publishes no CAD for this one.
2. **Logitech's own product page does** ship a 3D model, though — the *"view in your room"* /
   AR preview that lets you rotate the webcam in the browser. That viewer loads a plain glTF
   binary asset, served from Logitech's CDN:

   ```
   https://resource.logitech.com/content/dam/logitech/en/ar-models/webcams/brio-100/brio-100-graphite-webcams-ar-360.glb
   ```

   (there is a matching `…-usdz-360.usdz` for iOS AR).
3. **The `.glb` was parsed by hand.** No mesh tooling was available in the environment
   (`trimesh`, `pygltflib`, Blender, assimp — none installable), so the container was
   unpacked directly with stdlib Python `struct`/`json`: read the glTF chunk table, walk the
   accessors/buffer views, pull the vertex and index arrays out of the binary chunk, and
   write the meshes back out as STL. Those exports are kept in [hardware/reference/](hardware/reference/):
   - `brio100-camera-head.stl` — the camera body itself
   - `brio100-monitor-clip.stl` — the monitor hanger, kept for context
4. **The mesh was measured by rasterization.** Again with no CAD library available, the STL
   was rendered into depth-map slices with a small custom Z-buffer renderer (Python + PIL)
   and scanned for features: the lens shows up as a ~10 mm circular recess at
   `(X=-15.8, Y=31.0)`, and the front/back faces around the LED are genuinely flat and
   parallel, ~17.9 mm apart. Those coordinates are what the `.scad` files are built from.
5. **Cross-checked against the physical camera** with a tape measure — bezel diameter, LED
   offset from the lens, housing depth. The mesh numbers and the hand measurements agree —
   except the first housing-depth reading, which came out about 1 mm short (see
   [Clip versions](#-clip-versions)).

You can see the fit yourself: open [hardware/clip/brio105-sensor-clip-v1.2.scad](hardware/clip/brio105-sensor-clip-v1.2.scad) in
OpenSCAD with `show_reference = true` and the reference mesh is `import()`-ed in ghost mode,
in the same coordinate frame, with the clip sitting on it.

### ⚠️ The one unverified assumption

The AR asset Logitech publishes is for the **Brio 100**, not the **105** — no Brio 105 AR or
CAD model could be found anywhere. Product photos strongly suggest the two share a housing
and mould, but this has **not** been confirmed. Check a printed part against your real Brio
105 before trusting the fit. Other open points are listed under
`STILL UNVERIFIED` in the `.scad` header.

## 📦 What is here

| File | What it is |
|------|-----------|
| `hardware/clip/` | The spring clip ("hairpin" style) that grips the flat front/back faces beside the LED — v1.2 (latest), v1.1 and v1.0, each `.scad` + `.stl`, plus the tape-measure photo the fit is based on. See its [README](hardware/clip/README.md) |
| `hardware/enclosure/` | Desk enclosure for the Seeed XIAO ESP32-C6 — snap-together tray and lid, holding the board, the 10k load resistor and the sensor-cable junction. Tray and lid as separate STLs; `part = "both"` in the `.scad` puts them on one plate. Also holds the XIAO reference model, `include`-ed as a ghost preview. See its [README](hardware/enclosure/README.md) |
| `hardware/pod/` | Alternative attachment: a magnetic sensor pod plus a stick-on anchor. Holds the TEPT4400 and acts as the light shroud. Rotationally keyed so it can only re-attach the right way round. |
| `hardware/reference/` | The STL meshes extracted from Logitech's AR asset (reference only — not printable parts) |
| `hardware/wiring/` | [Wiring and first tests](hardware/wiring/README.md) — the circuit, the two wiring layouts and the no-solder tests for the board, with the drawings in `hardware/wiring/img/` |
| `firmware/` | [Toolchain and tests](firmware/README.md) — what to install, how to run the three board tests, and where the Arduino functions come from |

**Sensor:** TEPT4400 phototransistor. **Print:** matte black PETG or ABS — glossy filament
reflects stray light down the tunnel and defeats the shroud. Per-part print notes are in each
`.scad` header.

## 🧬 Clip versions

Three versions live in [hardware/clip/](hardware/clip/README.md). They are geometrically
close, but they reach their fit in different ways, and v1.2 rebuilt the spring so the grip no
longer depends on the exact housing thickness — the earlier two flipped between *cracks on
fitting* and *falls off* with half a millimetre of error.

Prints of v1.1 and v1.2 are on order for a test fit; neither is confirmed yet. The clip's own
README has the full comparison and the print orientation, which matters more than the
material on this part.

---

## 🧰 Controller enclosure

The clip holds the phototransistor on the camera; the other end of the cable lives in a
free-standing desk box — a bare XIAO ESP32-C6, the 10k load resistor and the cable junction,
with USB-C plugged in for power. Two snap-together printed parts, built on Seeed's own KiCad
geometry rather than on a published drawing, since their wiki and datasheet disagree about the
board size.

See [hardware/enclosure/](hardware/enclosure/README.md), and
[hardware/wiring/](hardware/wiring/README.md) for what goes inside it.

## 🔌 Alternative: if you *can* install software

If the machine is yours, skip the hardware entirely.
**[micam-watcher](https://github.com/GrzesiekGdn/micam-watcher)** is a small cross-platform Go
service that detects camera *and* microphone activity from the OS itself — `lsof` on
`/dev/video*` and `pactl` on Linux, registry keys on Windows — and POSTs to the same kind of
Home Assistant webhook. No printing, no soldering, and it covers the microphone too, which a
camera LED cannot tell you about.

| | this project | micam-watcher |
|---|---|---|
| Needs software on the monitored machine | no | yes |
| Works on a locked-down / corporate machine | yes | usually not |
| Detects camera | yes | yes |
| Detects microphone | no | yes |
| Camera / OS specific | fits the Brio 105 housing | Linux & Windows |
| Effort | print, wire, calibrate | install a service |
